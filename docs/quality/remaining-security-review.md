## Prioritized implementation plan, not changes made

1. **QA scratch custody:** fresh secure private scratch root, report/scratch separation, bounded QA_RUN, cleanup after browser termination. Tests must plant a symlink/preexisting path and vary umask, verify no foreign file changed, and check failure cleanup without launching real services.
2. **Git executable custody:** do not merely switch to shell=true or append a guessed safe PATH. Establish an explicitly configured absolute Git binary for supported Linux/Windows environments; verify canonical executable/ancestor ownership and writability according to the supported deployment trust model, then invoke without shell and with controlled environment. A path resolved from ambient PATH is not independent trust. Never silently chmod system directories or change machine security settings. Test a fake Git in a writable PATH directory, missing/non-executable path, symlink policy, nonzero exit and genuine inventory/digest behavior. Existing artifact/inventory tests need extending, not claiming they already test PATH attacks.
3. **DB transport compatibility:** retain current loopback fixture capability while rejecting accidental remote plaintext. Parse URLs explicitly; require wss/https for non-loopback endpoints by default. Require an explicit, documented opt-in for non-loopback ws/http in isolated networks if compatibility must be retained; this remains an acknowledged security exception, not a claim the rule is fixed universally. Do not classify RFC1918 or a Docker hostname as automatically confidential. Existing SURREAL_URL overrides also require validation, not just the legacy constructor. Do not change ws to wss blindly: the server may lack TLS. Expose an actionable error for remote legacy addresses directing users to configure TLS, with a migration/deprecation plan. Test localhost/127.0.0.1/::1, bracketed IPv6 ports, malformed URL/credentials, remote host/IP, explicit secure URLs and any approved opt-in; never connect to a user's database. `tests/test_database_url.py` locks legacy behavior and must be deliberately updated rather than broken silently.
4. Review narrow safe-allocator cases individually after evidence review. Do not convert all seven S5443 findings to false-positive as a batch. Audio retention and unsafe QA reuse are materially different from secure allocation.

## Candidate v2 credential format (design only; S2053 remains OPEN)

Preserve v1 PBKDF2 salt/600000 cost and unmarked SHA256 legacy decryption byte-for-byte. New writes could use a fresh cryptographic random 16-byte salt per value and a distinct envelope `pbkdf2v2:<canonical-base64url-salt>:<fernet-token>`. The fixed v2 protocol defines PBKDF2-HMAC-SHA256/600000/32-byte key; no attacker-controlled unbounded iteration field. Store the public salt beside the token, not as a separate per-install secret. Bound envelope/token length and require exact salt length/canonical encoding before KDF work. Domain-separate the v2 KDF input with a documented constant plus the random salt; validate that framing and decoding cannot confuse versions.

Dispatch decryption by version, with no fallback on malformed recognized version or wrong key. v2 salt tampering changes the derived key and must fail Fernet authentication. Unknown version markers must fail closed rather than be returned as plaintext. Retain historical plaintext fallback only for the established unmarked legacy path; explicitly test marker-like plaintext handling. Preserve valid already-versioned encryption input without double-wrapping; any migration must be a separate explicit operation, not an incidental read/save. No unbounded global cache indexed by attacker-supplied salts. Per-value KDF cost will be higher than current cached single-key derivation: benchmark synthetic batch reads and bound work/concurrency, not weaken authentication or cost silently.

Golden vectors must pin v1 and legacy compatibility; add deterministic test-only v2 vectors plus fresh-write randomness, salt/marker/token tampering, wrong-key, truncation/oversize, canonical decode and mixed-corpus tests. Exercise migration with synthetic records only: preflight/read-only inventory, decrypt-then-verify new value, per-record atomic compare-and-swap to avoid concurrent-write loss, idempotent resume, dry-run, and backup/rollback plan. Readers supporting v2 must deploy before enabling v2 writes. Old applications cannot read v2; downgrade after writes requires an appropriate verified backup or explicit conversion, never a salt edit. Key rotation is distinct from random salts and remains separate design work.

Fernet provides authenticated tokens; password-derived keys require retained salts. See [Cryptography Fernet documentation](https://cryptography.io/en/latest/fernet/). The proposed versioning, limits and migration mechanics above are project-specific design proposals, not a claim of implemented or independently audited cryptography. No existing records, keys, salt values, deployments, or stored ciphertext were touched.
