# T3b Atomic Note Revisions Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` task-by-task on one integration branch. The user waived a plan-review pause; self-review is included below. This document authorizes no deployment, external writes, credentials, or tool installation.

**Goal:** Prevent lost editorial updates across personal and legacy note writers, with coherent native/snapshot persistence and draft-preserving Web conflicts.

**Architecture:** Native `note.revision` is authoritative. One focused lower-level note-write coordinator owns conditional updates, transaction acknowledgements, and coordinated deletion; existing routes/domain APIs adapt to it without a domain/router rewrite. Project barriers coordinate local export/import, while DB transactions/CAS—not flock alone—provide durable revision safety.

**Tech Stack:** Existing async Python/FastAPI/Pydantic, SurrealDB 2.3.10, pytest, Next.js/TanStack Query/Vitest.

**Spec:** `docs/v1/MULTICLIENT_IMPLEMENTATION_PLAN.md` T3; `docs/7-DEVELOPMENT/decisions/ADR-014-atomic-note-revisions.md`. Canonical files inspected read-only on 2026-10-21. T3a commit `264a338` supplies schema/exporter fixtures, **not** `api/personal_contracts.py`; T3b introduces focused typed note models.

## Ownership and constraints

- One contracts/backend owner, one isolated branch based on reviewed T3a, sequential checkpoints below. Same owner integrates Web conflict changes; no parallel edits to `api/main.py`, models, exporter snapshots, `StudyWorkbench.tsx`, or portable service. T4/T5 receive a handoff rather than competing edits.
- No route renaming, authentication changes, cookie migration, general repository abstraction rewrite, offline queue, merge engine, or automatic write retry.
- `STUDY_WORKBENCH_NOTE_WRITE_MODE=legacy_single_web|multiclient`; default **legacy_single_web** throughout compatibility work, until explicit session-mode activation in T4/T5. Invalid configuration fails closed at startup. Supplied revision is always enforced. Multiclient update without revision returns 428. No claim of multiclient release readiness while omission remains allowed.
- `Revision = Annotated[int, Field(strict=True, ge=1)]`. Reject bool, float, numeric string, zero, negative. Missing persisted legacy revision means 1; malformed persisted revision is corruption, not a silent reset. Request `expected_revision: Revision | None = None`; explicit null is omission. Never persist it.
- Separate create/update/response models; creation returns revision 1 and requires no predecessor. Personal full-payload semantics remain unchanged; legacy PUT still changes only supplied fields, applied to the current transaction row rather than a stale preloaded full object.
- 409 body: `{"detail":{"code":"NOTE_REVISION_CONFLICT","current_revision":2}}`. 428 body: `{"detail":{"code":"NOTE_REVISION_REQUIRED"}}`. Typed exceptions in `open_notebook/exceptions.py`, global handlers with `_cors_headers` in `api/main.py`; catch-all routers rethrow `OpenNotebookError`. Malformed request revisions use existing FastAPI 422 `detail` validation-list envelope. Foreign/missing membership returns existing 404 **before** exposing revision.
- Preserve native `created` and snapshot `created_at`; increment revision once per successful editorial update, including citation/scope-only updates. Embedding-only updates never increment it. No embeddings on conflict/failed transaction; best-effort submission only after confirmed commit.
- Existing shared/flock-capable data-root assumption remains. Cross-host CAS safety must be real-DB tested; this is not a claim of fully distributed export coordination.

## Review focus

1. Old native-only notes and shared notebook membership: verified membership, not snapshot existence, controls personal edit access (Tasks 2–3).
2. Cancellation after commit versus before acknowledgement: unknown outcome must never be claimed as rollback or retried automatically (Task 2).
3. Legacy PUT/drop-through `Note.save()` and notebook cascade: no alternate editorial writer or resurrection (Task 3).
4. Old archives versus conflicting native/snapshot revisions: compatibility cannot silently select a lower revision (Task 4).
5. Late save response, refresh, and switching editor: server base revision is not local editor-generation state (Task 5).
