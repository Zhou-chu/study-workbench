## Shared creation draft and navigation contract (B3 review fix 1, F26)

AppProviders owns one memory-only DraftRegistry for the lifetime of the mounted app, outside route components and outside the server QueryClient cache. WorkbenchSession uses that same instance for retirement and its single navigation controller. A route unmount, Cancel, query cache clear or successful different creation does not remove earlier creation records. Nothing is serialized to browser storage. Reloading/closing the app still loses memory; beforeunload warns while any unfinished creation/editor/question/File remains.

A DraftState may contain a typed NotebookCreationDraft, separate from EditorModel. Its context is the exact frozen DispatchContext; its name/description and state are immutable snapshots. States are editing, pending, unknown, not-sent and succeeded. A confirmed success records the returned notebookId without renaming it. DraftId uses a reserved local @notebook-creation namespace, original epoch and UUID editorSession; it is neither a server notebook ID nor an idempotency key.

- getNotebookCreationSnapshot() returns the active creation entry and retained earlier unfinished entries, with stable snapshots for subscription. get(id) retains all original records, including succeeded receipts.
- openNotebookCreation(context) reopens the existing unfinished intent without rebinding input/capture. A new blank intent is created only on explicit open after a confirmed prior success, or by startFreshNotebookCreation(context) for a different current ready epoch. F25's explicit fresh action never copies old input.
- editNotebookCreation(id, {name?, description?}) changes only editing/definitely-not-sent, non-retired records. beginNotebookCreation(id, currentContext) atomically enters pending only for that valid original ready capture and nonblank name. It is the synchronous duplicate latch, not a server guarantee.
- settleNotebookCreation(id, outcome, currentContext) settles only pending original ownership. A real nonempty result ID can become succeeded only in the matching current scope. Unknown, retired or mismatched outcomes stay check-only; late not-sent/success cannot clear an already unknown lock. Retirement freezes old input and makes an old pending creation unknown. No observer/retry queue is introduced.
- useNotebookCreationDrafts() subscribes to this registry and registers the active creation with the existing WorkbenchSession navigation controller. It restores the same record after route remount. navigationPending() reports an already captured user-navigation decision; successful creation records and refreshes the list but cannot auto-navigate over that newer intent. It never creates another blocker or patches history. Owner-checked deactivate(id) cannot clear a newer notebook-question/editor activation.

F26 adds the explicit retain navigation decision only for typed creation pending/unknown state. The confirmation captures destination, original DraftState reference/revision, activation and decision kind. Keep creation and continue allows exactly that route while leaving the record, input, identity/capture, pending latch/unknown status untouched. It is not cancel, discard, resolution, unlock or retry. A changed record, stale callback, or A-to-B-to-A activation invalidates confirmation. The same React Router blocker performs navigation repair and continuation. Dirty unsent creation uses the existing confirmation. Beforeunload still considers retained older unknown records even when the current successful independent intent may navigate normally.

Ordinary note/editor saving, unknown, conflict and rejected states remain blocked with no generic-discard path. The creation retain branch cannot override such an EditorModel. B4-B9 must use these shared ownership/retirement contracts rather than component-local uncertainty flags or a parallel guard. API/auth/capability checks remain authoritative; registry readiness never establishes authentication itself.

## B4 source, selection and operation contract

B4 mounts one source row per source with version details, classic links, exact IDs/timestamps and provenance. Source reads emit `SourceReadIntent = { source_version_id, evidence_id?, page_index? }`; they never save or change question scope. B6 owns the actual source-read adapter and reader. A callback dispatch is not completed PDF-reader integration.

`useAppDrafts().sources` is the single app-lifetime memory owner for source operations and original File objects. `captureUpload` reads and hashes selected bytes before admission, captures the original immutable DispatchContext, and returns a Promise of the local operation ID/key. Exact same notebook/source/file metadata plus SHA-256 reuses the original record, including retained unknown/retired/succeeded records. Changed target or bytes get separate IDs. No browser document persistence, background queue, automatic mutation replay, or additional server guarantee is introduced.

`capture`, `begin`, and `settle` own immutable selection/web/remote/cancel payloads and A4 OperationTokens. `begin` is synchronous; duplicate handlers cannot dispatch twice. `settle` requires the exact original token, privacy context and session generation. Unknown and retired records cannot be rebound or replayed. Only a branded locally not-dispatched attempt can remain explicitly submit-ready. Unknown source operations block the existing navigation controller; they do not inherit creation's keep-and-continue exception.

`beginCheck` captures a separate current read token; `check` rechecks that read generation and original write-token ownership before accepting authoritative workspace-view evidence. This permits read-only reconciliation after a same-scope session refresh without changing the original write token. Upload recovery requires one exact original-key extraction job and one matching version/source/notebook. Missing, ambiguous, retired or malformed evidence is inconclusive and never grants permission to POST again. Generic GET job is not used for polling or recovery.

`useSourceSelection(notebookId, epoch, workspace)` provides `selection`, its original `operation`, and `unconfirmed`. B5/B9 must honor `unconfirmed` rather than silently accepting another scope while a write is unresolved. `includeImported` is explicit, preserves existing engine/origin/reading and both actual source lists, and rejects more than 20 instead of truncating. No upload/import or read implicitly includes content.

`useWorkbenchSnapshot` is a read-only controller subscription. Google controls require app readiness, no provider reauthentication flag, an explicit verification and the actual operation capability. Verification is never run on startup and may resume existing confirmed remote read-phase jobs. Provider account continuity is not inferred from endpoint, label, status or capability. Local uploads use the independently authenticated source byte limit and remain available when Google needs reauthentication.

Discovery is explicit/IME-safe, preserves provider/time/URL/snippet metadata, confirms the exact selected URLs and notebook before imports, and can stop only not-yet-submitted items. Remote listing pagination is bound to its target generation; confirmation is separately bound to target and exact selected IDs. Neither a changed target nor an A → B → A transition revives a stale action. All new source safety labels are explicit in all fourteen locales.

### B4 review round 1: selection reads, picker admission and provider evidence

A successful local selection payload is no longer a permanent overlay. The source registry exposes `beginWorkspaceRead(notebookId, context, generation) -> SourceWorkspaceReadToken` and `acceptWorkspaceRead(token, workspace, currentContext, generation) -> boolean`, with `getSelectionRead(notebookId)` for the accepted selection. NotebookPage brackets its real workspace query with these methods. The token captures the exact latest selection-operation snapshot at read start; the registry admits only its latest read token, matching notebook/context/generation, unchanged operation ownership, and either no local operation or an already-succeeded one. Reads begun before a new intent or before settlement cannot release that overlay. Unknown selection is not resolved by background refresh: it still requires explicit check-only recovery. The accepted DTO is copied/frozen in app memory, independently of query-cache structural sharing. No server revision, cross-tab CAS guarantee or retry permission is invented.

`useSourceSelection` keeps its `{ selection, operation, unconfirmed }` interface. B5/B9 must use the returned selection and honor unconfirmed; they must not substitute the old operation payload after a successful overlay has yielded to an accepted authoritative read. A new intent supersedes older read evidence. Generation is checked when a read is accepted; an already-accepted same-epoch value remains the last known selection across application refresh rather than falling back to the older succeeded payload. A successful operation remains retained for identity/status history, not as a forever-authoritative current selection.

File-picker admission now has a monotonically changing picker revision and explicit hashing state. Every change synchronously invalidates the previous batch before asynchronous byte hashing. Only the latest completed batch, exact target, current context/session generation and still-mounted/open picker can populate or submit. Clear, close, target change, context retirement and unmount retire earlier picker batches. The app registry still retains original Files/keys; stale picker completion never rebinds or discards those records. A-to-B-to-A file choice cannot revive the intervening B result.

`SessionSnapshot.providerEvidenceRevision: number` is a public **generation fence only**. It increases on every accepted NEEDS_REAUTH invalidation (including repeated errors while the flag is already true), when a new explicit provider verification begins, and after successful verified status. Shared callers of the same in-flight verification share that attempt; no extra verification is started automatically. This field is not account identity, proof of provider continuity, a capability or permission to replay an operation. F20/F22 application epoch, session generation, ready state, authenticated repair and local upload availability remain independent.

B4 captures providerEvidenceRevision in verified capability evidence, loaded source pages, pending list requests and confirmations. Synchronous controller-snapshot comparison fences event admission and late responses, including rapid true-to-false flag transitions that React might batch. Old pages are hidden, old confirmations stay non-actionable, and a late remote mutation receipt remains unknown if its captured provider evidence retired. Explicit successful verification does not revive previous loaded Google state. Import/association requires selected remote IDs to be present in a fresh valid listing; persisted selection is not silently cleared. Sync of selected local originals still uses a fresh explicit capability-bound confirmation of the exact linked target and local IDs, without treating an old remote page as authority. B5/B9 provider-dependent data/confirmations must capture and compare this revision in addition to their application/turn/operation fences; they must not watch only the boolean recovery flag.
